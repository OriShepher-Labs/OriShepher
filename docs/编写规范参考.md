# C 语言命名规范精简笔记

 C 语言命名规范笔记，重点参考了 Linux 内核风格与现代 C 项目常用实践。

## 📌 C 语言命名规范速查表

| 类别 | 推荐风格 | 示例 | 备注 |
|---|---|---|---|
| 局部变量 | snake_case | user_count, temp_ptr | 全小写，单词下划线分隔 |
| 全局变量 | g_snake_case | g_system_state | 加 g_ 前缀以示警戒 |
| 函数名 | snake_case | get_user_name(), init_hw() | 动词 + 名词形式 |
| 宏/常量 | ALL_CAPS | MAX_BUFFER, PI_VAL | 全大写，下划线分隔 |
| 枚举值 | ALL_CAPS | COLOR_RED, STATE_IDLE | 通常带有模块名前缀 |
| 结构体名 | PascalCase | struct UserInfo, struct Node | 首字母大写（或全小写） |
| 自定义类型 | _t 后缀 | uint32_t, config_t | 通过 typedef 定义的类型 |
| 文件命名 | snake_case | main_logic.c, usb_driver.h | 避免空格和特殊字符 |

## 📂 常用缩写与简写对照

为了保持 C 代码的简洁性，开发者通常使用以下约定俗成的缩写：

### 1. 通用技术缩写

| 全称 | 缩写 | 常用变量名示例 |
|---|---|---|
| Pointer (指针) | ptr | data_ptr, p_next |
| Buffer (缓冲区) | buf | recv_buf, tmp_buf |
| Length (长度) | len | str_len, msg_len |
| Count (计数) | cnt / num | user_cnt, retry_num |
| Index (索引) | idx | arr_idx, i (循环用) |
| Address (地址) | addr | dest_addr, ip_addr |
| Configuration (配置) | conf / cfg | sys_cfg, init_config |

### 2. 状态与布尔缩写

| 全称 | 缩写 | 常用变量名示例 |
|---|---|---|
| Initialize (初始化) | init | init_uart(), is_inited |
| Synchronize (同步) | sync | sync_data(), async_mode |
| Previous / Next (前一/后一) | prev / next | node->prev, p_next |
| Temporary (临时) | tmp / temp | tmp_val, temp_file |
| Source / Destination (源/目的) | src / dest / dst | memcpy(dst, src, n) |

## 💡 命名核心原则 (Best Practices)

- **见名知意**：变量名应描述"它是什么"，函数名应描述"它做了什么"。
  - ❌ `int a;`
  - ✅ `int student_age;`

- **避免"匈牙利命名法"**：在现代 C 中，不要在变量名前加 i (int) 或 f (float)，这会让代码显得过时且难以维护。

- **循环变量例外**：对于极短范围内的循环，使用 i, j, k 是被允许且推荐的标准做法。

- **模块化前缀**：在大型项目中，函数名常带模块名前缀。
  - 例如：`wifi_connect()`, `wifi_disconnect()`。

## 🔧 大型 C 语言项目规范化指南

在多人协作的大型 C 语言项目中，“命名规范”只是冰山一角。为了防止代码变成“只有上帝和写代码的人能看懂”的乱麻，以下几个维度的规范化至关重要：

### 1. 工程结构与头文件规范

大型项目最怕“头文件地狱”（包含冲突或重复包含）。

| 规范点 | 核心要求 | 示例/说明 |
|---|---|---|
| 头文件卫士 | 必须使用宏保护，防止重复编译 | `#ifndef MODULE_NAME_H ...` |
| 包含顺序 | 建议：标准库 -> 第三方库 -> 项目内其他头文件 -> 本模块头文件 | 减少隐式依赖冲突 |
| 目录结构 | 严格区分 src/, include/, tests/, docs/ | 不要把所有文件堆在根目录 |
| 减少暴露 | 只有外部需要调用的函数放 .h，私有函数用 static 留在 .c | 遵循“最小暴露原则” |

### 2. 代码格式化 (Formatting)

不要浪费时间在争论“空格还是 Tab”上，直接通过工具强制统一。

* **统一缩进**：通常为 4 个空格（Linux 内核为 8 个 Tab，视项目而定）。
* **大括号风格**：
  * K&R 风格（左大括号不换行）：`if (condition) {`
  * Allman 风格（左大括号换行）：`if (condition) \n {`
* **工具约束**：项目根目录放置一个 .clang-format 文件，所有人提交前运行脚本自动格式化。

### 3. 注释与文档规范 (Doxygen)

代码是写给人看的，注释放哪里、怎么写需要统一。

* **函数头注释**：必须包含：功能描述、参数说明（In/Out）、返回值含义、调用限制。
* **复杂逻辑注释**：不要解释“这段代码在做什么”，要解释“为什么要这么做”。
* **TODO 标记**：统一格式，如 `// TODO(姓名): 待优化逻辑`，方便后期全局搜索。

### 4. 内存与错误处理规范 (Critical)

这是 C 语言项目崩溃的重灾区。

| 规范类别 | 推荐实践 |
|---|---|
| 错误返回 | 统一返回 int（0 为成功，负数为错误码）或使用统一的 error_t 枚举。 |
| 入参校验 | 所有 public 函数必须在开始处检查指针是否为 NULL。 |
| 资源释放 | 遵循“谁申请谁释放”原则，或统一使用 `goto cleanup;` 模式处理多处报错退出。 |
| 禁止魔数 | 严禁在代码中出现 `if (status == 3)`，必须使用宏或枚举：`if (status == ERR_TIMEOUT)`。 |

### 5. 编译与自动化规范

* **警告即错误**：在 Makefile 中开启 -Wall -Werror。这强制要求所有开发者必须处理编译器警告，不允许带病上线。
* **静态分析**：强制在 CI（持续集成）流程中运行 cppcheck 或 Clang Static Analyzer。
* **版本控制**：Git 提交信息（Commit Message）规范化，例如使用 feat:, fix:, docs: 等前缀。

### 6. 接口设计规范 (API Design)

* **高内聚低耦合**：模块之间通过定义的接口通信，禁止直接访问其他模块的全局变量。
* **防御性编程**：假设调用者传入的数据都是坏的，假设分配内存可能会失败。

## 💡 核心建议

在大型项目中，“一致性”胜过“完美”。哪怕一套规范不是最科学的，只要全员严格遵守，项目就是可控的。
